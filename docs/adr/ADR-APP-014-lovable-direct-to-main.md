# ADR-APP-014 — Lovable's direct-to-`main` write path

- **Status:** Proposed
- **Date:** 2026-09-10
- **Deciders:** Amir (product owner), implementation agent
- **Money-adjacent:** No directly — but it governs the path by which
  money-adjacent migrations reach a live database, so a change here changes the
  blast radius of every OD-001 decision.
- **Serves:** Task 8 of the 2026-09-10 audit brief

> **This ADR deliberately makes no choice.** It lays out the options and their
> consequences. Choosing is the owner's, and implementing branch protection
> without that choice could lock the agent out of `main` in the middle of a
> migration sequence — which is the one failure mode worse than the problem.

## Context

`main` deploys live through Lovable the moment it merges. Two writers reach it:

| Writer | Path | Gate |
|---|---|---|
| Claude Code | branch → PR → CI (`boot-gate`, CodeQL) → merge | full |
| `gpt-engineer-app[bot]` (Lovable) | direct commit to `main` | none |

### What the numbers say, and how they have changed

The audit brief, written this morning, reported the last 120 commits as
**62 Claude / 41 majabri / 17 Lovable**. Measured today over the last 120
commits (2026-09-05 → 2026-09-10):

| Author | Commits |
|---|---|
| `gpt-engineer-app[bot]` | **46** |
| Claude | 37 |
| majabri | 32 |
| dependabot | 5 |

**Lovable is now the largest single author of recent history, not the
smallest.** Twenty-nine of those 46 landed today alone. Thirty-five of the 46
are single-parent commits straight onto `main`; the other 11 are Lovable merging
`main` back into its own line.

Where this ADR and the brief disagree on this point, the repository wins, and
the direction of the change is the material fact: the ungated path is growing,
not shrinking.

### It is not a side channel — it is the only channel for migrations

Of the last 120 commits touching `supabase/migrations`:

| Author | Commits |
|---|---|
| `gpt-engineer-app[bot]` | **25** |
| Claude | 20 |
| Amir (three name spellings) | 9 |

Lovable authors *more* migration commits than the agent does. This is not an
accident of tooling: **Lovable is the only way a migration reaches Lovable
Cloud.** A migration merged through a PR and never run through Lovable is a file
in the repository and nothing in the database — which is the state
`20260910150000_cash_flows.sql` is in as this is written.

### What has actually gone wrong

1. **Re-authoring.** Lovable does not run the repository's copy of a pending
   migration. It writes a **fresh file** with a new timestamp and UUID name and
   applies that. Twice this week the re-authored copy carried a string the
   personal-data guard forbids, and `main` went red on merge — repaired by #178
   and #179.
2. **No boot gate.** Nothing checks that `main` still boots after a Lovable
   commit. On 2026-09-08 the schema shim it removed was fine; the risk is that
   nothing would have told us if it had not been.
3. **Generated types drift silently.** `src/integrations/supabase/types.ts` is
   regenerated by Lovable when it applies a migration. A migration merged but
   not applied leaves the types describing a schema the database does not have,
   and the only signal is a `select` failing at runtime.

### What has NOT gone wrong

`main` has been green at every point this session where it was measured, and
every red `main` this week was caught by a guard within minutes. The existing
guards — `personalData.test.ts`, `generatedDatabaseTypes.test.ts` — were written
precisely for this path and have done their job. The case for changing anything
rests on the trend and on the absent boot gate, not on a history of undetected
damage.

## Options

### A. Leave it. Rely on guards and on `main` being watched.

- **For.** Nothing can lock the agent or the owner out. Migrations keep their
  only working path. The guards already catch the failure mode that has actually
  occurred, and they catch it in CI on the next PR rather than in production.
- **Against.** Detection is after the fact and after deployment. A Lovable
  commit that breaks the boot is live until somebody notices. The window is
  however long it takes a human to look.

### B. Branch protection on `main`, with Lovable exempted.

- **For.** Claude and any future contributor go through CI; Lovable keeps
  working.
- **Against.** It formalises the ungated path rather than closing it, and
  protects the writer that has never broken `main` from the writer that has.
  This is close to backwards.

### C. Branch protection with no exemptions, and a separate migration route.

Lovable is pointed at a `lovable/*` branch; a scheduled job or the agent opens
a PR from it; migrations reach the database through a reviewed merge.

- **For.** One gate for every writer. Nothing reaches a live deployment
  unbooted.
- **Against.** **This is the option that can lock everyone out.** It depends on
  Lovable being configurable to a non-default branch — unverified — and if it
  is not, migrations have no route at all until it is undone. Undoing it
  requires repository-admin access at a moment when the app cannot ship a
  schema change.

### D. A post-hoc boot gate on `main`.

A workflow that runs on every push to `main` (not only on PRs), boots the app
and runs `bun test`, and opens an issue — or reverts — on failure.

- **For.** Closes the detection gap without touching who may write. No lockout
  risk of any kind. Implementable this week and independent of A/B/C.
- **Against.** Still after the fact: a broken `main` has already deployed. It
  shortens the window rather than removing it.

## Recommendation, offered not taken

**D now, and a decision on A/B/C separately.** D is the only option with no
lockout risk and it addresses the gap the evidence actually supports — that
nothing checks a Lovable commit at all. A, B and C all turn on a question this
ADR cannot answer from the repository: **can Lovable be pointed at a branch
other than `main`?** That is a question for the Lovable project settings, and
until it is answered C is a plan with an untested premise at its centre.

## Consequences

- Under **D**, the repository gains a workflow that runs on `push: main`.
  Expect it to be red occasionally on Lovable's own commits — that is the
  point, and each one is a real finding rather than noise.
- Under **C**, the migration checkpoint ritual changes shape: the agent would
  open the PR for a Lovable branch rather than handing over SQL.
- Under **A** or **B**, nothing changes and this ADR is the record of why.
- Whichever is chosen, `main` remaining the single source of truth and the
  no-history-rewrite rule are untouched.

## Not decided here

Whether the migration checkpoint ritual itself should change. Whether the
generated-types drift deserves its own guard asserting that every migration file
in the repository has been applied — that is a real gap, it is checkable against
the Supabase migration history, and it is a separate piece of work.
